# 로컬 인덱스와 연구 프로젝트

상태: 제안. 날짜: 2026-09-30. 결정 시점: P3 시작 전, 구현 검증은 P4. 관련 문서: [제품 요구사항](../01-product-requirements.md), [API와 데이터 모델](../04-core-api-and-data-model.md), [개발과 검증 계획](../06-development-and-validation.md).

## 배경

사용자는 로컬 폴더의 DICOM을 열고 연구 메모와 측정을 다시 사용하려 한다. 빠른 검사 목록을 위한 인덱스와 잃으면 안 되는 사용자 작업은 복구 성격이 다르다. 파일 이동, 이름 변경과 동일 UID의 다른 파일도 처리해야 한다.

## 선택 제안

원본은 사용자가 선택한 위치에서 읽는다. SQLite 인덱스에는 파일 위치와 조회용 메타데이터를 저장하고, 연구 작업은 버전이 있는 독립 프로젝트 문서에 저장한다. 초기 프로젝트 형식은 UTF-8 `.dview.json`으로 제안한다.

주석은 SOP Instance UID가 있으면 보존하면서 내용 해시와 DICOM frame number로 원본을 확인한다. 경로는 파일을 찾는 힌트로 사용하고 내용 동일성의 근거로 사용하지 않는다. 상대 경로와 macOS의 접근 권한 정보는 별개로 유지한다.

같은 영속 참조 규칙을 메모와 저장된 뷰 상태에도 적용한다. 세션의 instance/display set ID는 저장 복원의 키로 쓰지 않으며 인덱스를 다시 만들어도 참조를 복구할 수 있어야 한다. 다른 이름으로 저장하면 새 프로젝트 위치에 맞춰 상대 경로를 갱신한다.

프로젝트 저장은 임시 파일 작성과 교체, revision 충돌 검사, schema migration을 포함한다. 캐시와 인덱스를 재생성해도 사용자 주석이 사라지지 않도록 한다.

편집 revision과 저장 파일의 내용 revision은 분리한다. snapshot 저장 중 새 편집이 생기면 완료 후에도 변경됨을 유지한다. 앱 내부의 같은 대상 저장은 직렬화하고 외부 변경을 검사한다. 임시 파일 교체만으로 모든 외부 편집기와 원자적인 충돌 검사가 보장되는 것은 아니므로 마지막 유효 사본과 실패 복구를 별도로 검증한다.

## 검토한 대안

모든 DICOM을 앱 라이브러리로 복사하면 경로 관리가 단순해지지만 저장 공간이 늘고 사용자의 자료 정리 방식과 중복된다. 초기에는 원본 참조를 선택하고 라이브러리 복사 모드는 후속 후보로 둔다.

사용자 작업까지 하나의 앱 DB에 저장하면 transaction 관리가 편하지만 프로젝트를 따로 보관하거나 옮기기 어렵다. 별도 프로젝트 파일은 자료 연결 검증이 추가되는 대신 사용자 작업의 범위를 명확히 한다.

주석을 즉시 DICOM SR/SEG/Presentation State로 저장하는 방식은 다른 도구와의 교환에 유리할 수 있다. 초기 기본 측정과 메모에는 별도 형식을 사용하고 표준 DICOM 쓰기는 필요한 객체 의미를 설계한 뒤 추가한다.

## 결과

원본이 이동하면 재연결이 필요하다. 내용 해시 계산은 큰 파일에서 시간이 들므로 최초 연결과 저장 시 진행을 표시하고 source revision별로 재사용한다. 동일 UID의 전송 구문 변경 파일도 바이트 내용이 달라 자동 연결되지 않을 수 있다.

JSON schema와 migration을 관리해야 한다. SQLite 인덱스의 성공적인 기록이 프로젝트 저장 성공을 의미하지 않으며, 저장 상태를 구분해야 한다.

## 검증과 재검토

P4에서 원본 이동·교체, 저장 중 편집과 실패, 외부 수정 충돌, future schema, 메모와 측정 round-trip, 인덱스 재생성 후 뷰 상태 복원을 시험한다. 프로젝트가 매우 커지거나 segmentation 배열을 포함해야 하면 패키지 또는 DB 기반 프로젝트 형식을 새 ADR로 검토한다.
