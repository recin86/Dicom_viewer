# Rust 코어와 Swift 앱 분리

상태: 채택된 방향. 날짜: 2026-09-30. 근거: 사용자가 dicom-rs를 사용하는 Rust 코어와 Swift macOS 앱 구성을 명시했다. 이 기록의 채택 범위는 기술 방향이며, 모든 세부 모듈과 구현 방법을 이미 승인하거나 검증했다는 뜻은 아니다.

관련 문서: [제품 요구사항](../01-product-requirements.md), [시스템 아키텍처](../02-system-architecture.md).

## 배경

앱은 집의 Mac에서 CT/MR/X-ray/US 자료를 읽고 개인 연구에 사용한다. DICOM 의미 해석과 수치 검증을 UI와 독립적으로 수행하면서 macOS의 창, 입력과 표시 환경을 활용할 필요가 있다.

## 선택

Rust와 dicom-rs를 코어의 기반으로 사용하고 Swift로 macOS 앱을 만든다. 코어에는 파일 해석, 디코딩, 프레임 구성, 공간 정보와 수치 계산을 모으는 구조를 제안한다. Swift에는 창, 입력, 선택과 도구 상태 및 렌더러를 둔다.

코어는 앱에 포함한 라이브러리로 사용하는 작업안을 둔다. 프레임워크 연결 방법과 GPU 경계는 별도의 ADR에서 검토한다. 코어의 공개 타입에 Swift/Metal UI 타입을 넣지 않아 향후 다른 환경에서도 재사용할 여지를 둔다.

## 검토한 대안

Swift 단일 언어 구성은 언어 경계와 빌드 구성을 줄일 수 있다. Rust 단일 언어 UI는 코어와 UI 코드를 공유하기 쉽다. 현재는 사용자가 선택한 기술 방향과 macOS 네이티브 조작을 우선해 두 언어 구성을 따른다.

로컬 HTTP 서버와 Swift 클라이언트 구성은 프로세스 분리가 가능하지만 배포, 포트, 직렬화와 수명 관리가 추가된다. 현재 로컬 앱의 요구에는 라이브러리 연결을 먼저 검증한다.

## 결과

Rust와 Swift 각각의 빌드와 시험이 필요하고, FFI 및 메모리 소유권을 명시해야 한다. Rust 도입 자체를 성능 보장으로 해석하지 않는다. dicom-rs에 없는 뷰어 기능과 지원하지 않는 변환은 앱에서 구현하거나 제한을 명시한다.

## 검증과 재검토

P0에서 대상 Mac의 Rust 라이브러리 호출, 코덱과 프레임 전달을 검증한다. P1에서 UI 없는 픽셀·좌표 시험과 macOS 렌더링 시험을 분리할 수 있는지 확인한다. 플랫폼 요구나 UI 방향이 달라지면 이 결정을 재검토한다.
